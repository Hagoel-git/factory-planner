### 1.1 Critical Crash on Machine Renaming (`std::out_of_range`)
- **File**: [`src/core/data/GameDataManager.cpp:363-369`](file:///home/hagoel/Projects/factory-planner/src/core/data/GameDataManager.cpp#L363-L369)
- **Code**:
  ```cpp
  if (m_data.id_aliases.count(PREFIX_MAC + new_key)) {
      if (m_data.id_aliases.at(PREFIX_RES + new_key) != current_key) {
          LOG(WARNING) << "Name conflicts with a historical alias: " << new_key;
          outError = "Name conflicts with a historical alias.";
          return false;
      }
  }
  ```
- **Description**: The outer condition checks for the machine alias prefix `PREFIX_MAC + new_key`, but the inner lookup accesses `PREFIX_RES + new_key` using `std::map::at()`. If a machine alias exists in `id_aliases` without an identical resource alias key, `m_data.id_aliases.at(PREFIX_RES + new_key)` throws an unhandled `std::out_of_range` exception, terminating the program.
- **Remediation**: Change `PREFIX_RES` to `PREFIX_MAC`.

### 1.3 Silent Failure & State Corruption on JSON Loading Exception
- **File**: [`src/core/data/GameDataManager.cpp:165-172, 831-836`](file:///home/hagoel/Projects/factory-planner/src/core/data/GameDataManager.cpp#L165-L172) and [`src/app/Application.cpp:1309-1311`](file:///home/hagoel/Projects/factory-planner/src/app/Application.cpp#L1309-L1311)

  ```cpp

  } catch (const std::exception &ex) {
  ```

### 1.10 Global NFD Lifecycle Collision & Use-After-Free in Detached Dialog Threads
- **File**: [`src/app/main.cpp:172, 291`](file:///home/hagoel/Projects/factory-planner/src/app/main.cpp#L172), [`src/app/Application.cpp:1013-1043, 1125-1155`](file:///home/hagoel/Projects/factory-planner/src/app/Application.cpp#L1013-L1043), [`src/editor/game_data_editor/GameDataEditor.cpp:629-649, 763-784, 880-901, 1032-1055`](file:///home/hagoel/Projects/factory-planner/src/editor/game_data_editor/GameDataEditor.cpp#L629-L649), [`src/editor/settings_editor/SettingsEditor.cpp:63-73, 93-103`](file:///home/hagoel/Projects/factory-planner/src/editor/settings_editor/SettingsEditor.cpp#L63-L73)
- **Code**:
  ```cpp
  // Main thread:
  main() { NFD_Init(); ... NFD_Quit(); }

  // Detached worker thread:
  std::thread([this]() {
      if (NFD_Init() == NFD_OKAY) {
          ...
          NFD_Quit(); // TEARS DOWN GLOBAL NFD BACKEND FOR THE WHOLE PROCESS!
      }
      m_iconDialog.isRunning = false;
  }).detach();

  // SettingsEditor worker thread:
  std::thread([this]() {
      // Calls NFD_PickFolderU8_With WITHOUT NFD_Init() on torn-down library!
      nfdresult_t result = NFD_PickFolderU8_With(&outPath, &args);
  }).detach();
  ```
- **Description**:
  1. `nativefiledialog-extended` is not reference-counted. When any detached thread finishes and calls `NFD_Quit()`, it destroys the global NFD backend initialized in `main()`. Subsequent file dialogs in `SettingsEditor` fail or crash.
  2. The threads capture `[this]` while detached. If the window or application closes while a file picker is open, the thread writes to freed memory (Heap-Use-After-Free).
  3. `m_bufDefaultProjectPath` in `SettingsEditor` is written by a worker thread via `strncpy` while read every frame by the UI thread without synchronization (Data Race).
- **Remediation**: Keep NFD initialization/shutdown strictly on the main thread, join or cancel worker threads on editor destruction, and protect shared buffers with mutexes.

## 4. Deep Architectural Investigations (Resolving Prior Gaps)

### 4.1 Wayland Frame Timing & VSync Interplay (Resolved)
- **Finding**: In [`src/app/main.cpp:252-264`](file:///home/hagoel/Projects/factory-planner/src/app/main.cpp#L252-L264), the Wayland frame pacer unconditionally executes:
  ```cpp
  nextFrame += std::chrono::duration_cast<std::chrono::steady_clock::duration>(
      std::chrono::duration<double>(targetTime));
  std::this_thread::sleep_until(nextFrame);
  ```
- **Analysis**: If graph solving or rendering takes longer than `targetTime` (16.6ms at 60 FPS), `nextFrame` falls behind the steady clock. Because `nextFrame` is in the past, `sleep_until` returns immediately. As frames continue to exceed 16.6ms, `nextFrame` falls further and further behind, accumulating a negative latency debt. Once the workload eases, the application continues running without sleeping until `nextFrame` catches up, pegging CPU usage at 100%.
- **Solution**: Clamp `nextFrame = std::max(nextFrame, std::chrono::steady_clock::now())` at the start of each pacing calculation.

### 4.2 Native File Dialog Backend Multi-threading & Global Lifecycle (Resolved)
- **Finding**: `main()` calls `NFD_Init()` at startup and `NFD_Quit()` at exit. Background dialog threads in `Application.cpp` and `GameDataEditor.cpp` call `NFD_Init()` upon opening and `NFD_Quit()` upon closing.
- **Analysis**: In `nativefiledialog-extended`, initialization is global and not reference-counted. When a detached background dialog thread calls `NFD_Quit()`, the entire NFD subsystem is torn down process-wide. Subsequent dialog calls in `SettingsEditor.cpp` (which calls `NFD_PickFolderU8_With` without `NFD_Init()`) execute against an uninitialized backend. On Linux with GTK/Portal or Windows with COM apartment threading, calling `NFD_Init()`/`NFD_Quit()` across detached worker threads violates COM/GTK thread-affinity rules.
- **Solution**: Maintain NFD initialization strictly on the main thread for the entire application lifetime, and eliminate calls to `NFD_Init()` / `NFD_Quit()` inside worker threads.

### 4.3 Solver Numerical Stability & Call Stack Exhaustion on Extreme Graphs (Resolved)
- **Finding**: In [`src/core/graph/FactorySolver.cpp:421-472`](file:///home/hagoel/Projects/factory-planner/src/core/graph/FactorySolver.cpp#L421-L472), `computeNodeDepths` executes recursive `std::function` DFS calls (`dfs1`, `dfs2`, and `get_scc_depth`).
- **Analysis**: On graphs with deep sequential chains (e.g. 5,000–10,000 production stages connected end-to-end), recursion depth exceeds the OS thread stack size (especially on Windows MSVC with default 1MB stack size), resulting in a call stack overflow crash.
- **Solution**: Replace recursive DFS with an explicit `std::vector` stack or Tarjan/Kahn iterative algorithms.
